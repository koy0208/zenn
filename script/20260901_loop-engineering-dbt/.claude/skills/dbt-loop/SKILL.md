# dbt-loop

このプロジェクトを直すエージェントが、毎回ゼロから状況を推測しなくて済むようにするための知識。

## 実行方法

**dbt を直接叩かない。必ずゲート経由で回す。**

```sh
./bin/verify.sh
```

終了コードが判定のすべて。

| 終了コード | 意味 | 次にやること |
| --- | --- | --- |
| 0 | 全モデル・全テストが緑 | ループを終了する |
| 1 | dbt が落ちた | 出力された失敗を 1 件ずつ直す |
| 2 | 契約が改変された | **直ちに停止して人間を呼ぶ** |
| 3 | 症状を黙らせる修正パターンを検出した | 直し方を変える。理由を書けるなら `loop-ok: <理由>` |

個別のモデルだけ試したいときは以下。ただし合否判定は必ず `verify.sh` で取り直すこと。

```sh
uv run dbt build --project-dir jaffle-shop --profiles-dir jaffle-shop --select stg_orders
```

## モデルの粒度（これが仕様）

| モデル | 粒度 | 主キー |
| --- | --- | --- |
| `stg_customers` | 1 行 = 1 顧客 | `customer_id` |
| `stg_orders` | 1 行 = 1 注文 | `order_id` |
| `stg_order_items` | 1 行 = 注文明細 1 行 | `order_item_id` |
| `stg_products` | 1 行 = 1 SKU | `product_id` |
| `stg_supplies` | 1 行 = SKU ごとの副資材 1 種 | `supply_id`（`id` と `sku` の複合） |
| `stg_locations` | 1 行 = 1 店舗 | `location_id` |
| `fct_order_items` | 1 行 = 注文明細 1 行 | `order_item_id` |
| `fct_orders` | 1 行 = 1 注文 | `order_id` |
| `dim_customers` | 1 行 = 1 顧客 | `customer_id` |

`fct_order_items` は `stg_order_items` と同じ行数。
`dim_customers` は `stg_customers` と同じ行数。**注文実績のない顧客も必ず残す。**

## 規約

- ステージング層は `raw_*` ソースの読み替えだけを行う。集計もフィルタもしない。
- 金額カラムはセント単位で入ってくる。必ず `{{ cents_to_dollars('col') }}` を通してドルに直す。
- ソースの生カラム名（`sku`, `name`, `type`, `price`, `cost`, `customer`, `store_id`）は
  ステージングで意味のある名前に付け替える。下流は付け替え後の名前だけを使う。
- 1 対多の関係を join するときは、**join する前に多側を粒度まで畳む**。
- 左外部結合で NULL になりうる集計値は `coalesce(..., 0)` で埋める。

## やってはいけない直し方

赤を緑にする方法はいくつもあるが、以下は「直した」ことにならない。
`verify.sh` が終了コード 2 で機械的に弾くもの、レビュー側が弾くものの両方がある。

1. **テストを消す・ゆるめる。** `*.yml` の `data_tests` や `data-tests/*.sql` に触れるのは禁止。
   これは修正ではなく、失敗の報告をやめただけ。
2. **`distinct` で重複を潰す。** 行が増えているなら join が壊れている。
   `distinct` は原因を隠したまま行数だけ合わせる。
3. **`any_value()` で GROUP BY エラーを黙らせる。**
   DuckDB のエラーメッセージは `any_value()` を提案してくるが、
   その列が集計粒度で一意でないなら、出てくる値は「たまたま最初に見つかった行」でしかない。
   その列が本当にその粒度に属するのかをまず考える。属さないなら列ごと落とす。
4. **NULL を消すために `inner join` に変える。** 行が消える。粒度テストが落ちる。
5. **`where ... is not null` で失敗行を除外する。** 同上。

## 監査で数えたことは、テストにする

形のテスト（行数・主キー・NULL の有無）は、「重複を消す」タイプの修正で全部満たせてしまう。
値が間違っていても緑になる。だから監査役は毎回、値を手で数えることになる。

**手で数えたら、その場でテストに昇格させる。**

- 監査で `supply_cost` をソース側の合計と突き合わせたなら、
  同じ照合を `data-tests/` の 1 本にする。
- 次からその種類の間違いは、人間の判断ではなく終了コードで止まる。
- ゲートは一方向にしか動かない。ゆるめるのは契約違反、締めるのは人間の仕事。

テストを足すと契約ハッシュが変わるので、`verify.sh` は一度 exit 2 を返す。
これは正常。人間が `bin/ratchet.sh` 相当の手順でハッシュを記録し直す。
**エージェントが自分でハッシュを更新してはならない。**

## 状態の記録

各イテレーションの結果は `LOOP_STATE.md` に追記する。
モデルはセッション間で何も覚えていないが、このファイルは覚えている。

追記する内容:

- 何番目のイテレーションか
- `verify.sh` の status と PASS/ERROR 件数
- 今回直した失敗と、その原因（症状ではなく原因を書く）
- 変更したファイル
- 次に残っている失敗
