Loop Engineering × dbt — 実践レポート

ゲートは緑。値は40倍ズレていた。

わざと 6 個のエラーを仕込んだ dbt プロジェクトを、プロンプトを打たずに「直り続ける仕組み」で片付ける。 ループは 4 個を気持ちよく潰し、残り 2 個で見事に騙されました。 その騙され方のほうが本題です。

30 秒でわかる全体像

Addy Osmani の Loop Engineering が言っているのは、 エージェントにプロンプトを打つ「人間の役割」そのものを仕組みに置き換えろ、ということです。

I don't prompt Claude anymore. I have loops running that prompt Claude.

Addy Osmani, Loop Engineering

Why

dbt のエラー対応は「実行 → 読む → 直す → 再実行」で構造がいつも同じ。毎回プロンプトを打つのは、同じループを人間が手回ししているだけ。

What

Automations / Worktrees / Skills / Connectors / Sub-agents ＋ State の 6 要素を、dbt プロジェクトにそのまま実装する。

How

合格条件を verify.sh 1 本に落とし、終了コードを停止条件にする。作る役と検証する役を分け、進捗をリポジトリに残す。

ループの中身

ループで最初に決めるのは、プロンプトではなく停止条件です。 bin/verify.sh がそれを担い、終了コードだけで次の行動が決まります。

終了コード意味次にやること
0 全モデル・全テストが緑 ループを終了する
1 dbt が落ちた 失敗を 1 件ずつ直す
2 契約（テスト定義）が改変された 停止して人間を呼ぶ

3 番目が肝です。赤を緑にする最短ルートは、いつだってテストを消すことだから。 verify.sh はテスト定義の SHA-256 を握っていて、書き換えを機械的に検知します。

設計の急所 エージェントが採点基準そのものを書き換えられる状態で、ループを回してはいけません。

Addy の 5 要素との対応

Skill に書いた「やってはいけない直し方」

これがいちばん効きました。以下は全部「赤を緑にする」意味では成功してしまうので、 明示的に禁止しておかないと通ります。 

1. テストを消す・ゆるめる
2. `distinct` で重複を潰す
3. `any_value()` で GROUP BY エラーを黙らせる
4. NULL を消すために `inner join` に変える
5. `where ... is not null` で失敗行を除外する

実際に回した 6 周

仕込んだエラーは手前 4 つが構文の問題、後ろ 2 つが意味の問題という構成です。 コンパイルエラー → 実行時エラー → テスト失敗の順に、層が剥がれるように片付いていきます。

1〜3 周目は面白いところが何もありません。エラーメッセージに答えが書いてあるからです。 3 周目で構文エラーが尽き、ここから性質が変わります。

4 周目：ゲートが完全に騙される

Failure in test unique_fct_order_items_order_item_id
  Got 5795 results, configured to fail if != 0

Failure in test assert_fct_order_items_grain
  Got 1 result, configured to fail if != 0

原因は join のファンアウトです。stg_supplies は「SKU ごとの副資材 1 種」が 1 行で、 1 SKU あたり 4〜9 行あります。それを明細に直接 join したので、明細 1 行が副資材の数だけ複製されました。

重複を消しにいくと、こうなる

ここで「重複しているのだから 1 行に絞ればいい」と考えると、こう書けます。

select * from joined
qualify row_number() over (partition by order_item_id order by supply_cost) = 1

unique も粒度テストも通ります。行数を数えても正しい。 テストで検知できる要素は、すべて正しい。では中身はどうか。

order by supply_cost が最安の副資材 1 行だけを残していました。 全 SKU の原価が 0.04 に化けています。しかもこの値は下流 fct_orders.order_cost の材料です。

この記事の主張 テストが通ったことと、モデルが正しいことは別物です。 そして自動化されたゲートは、前者しか判定できません。

3 段構えの防御は、どこで止めたのか

5 周目：エラーメッセージ自身が罠を勧めてくる

Binder Error: column "location_id" must appear in the GROUP BY clause
  or must be part of an aggregate function.
  Either add it to the GROUP BY list, or use "ANY_VALUE(location_id)"
  if the exact value of "location_id" is not important.

DuckDB が親切に ANY_VALUE() を提案してきます。従うと通ります。 しかも今回のデータでは、その結果はたまたま正しい。 935 人全員が 1 店舗にしか紐づいていないからです。

それでも却下しました。理由は 2 つ。

  • location_id は下流で一度も参照されていません。誰も読まない列を、集計してまで残す理由がない。
  • 「顧客は 1 店舗にしか紐づかない」という不変条件は、モデルにもテストにもどこにも書かれていません。顧客が 2 店舗目で注文した日に、エラーも出さずに壊れます。
エラーメッセージが教えてくれるのは黙らせ方であって、直し方ではありません。

では、意味的エラーはどうするのか

ここまでを読むと「意味のエラーは原理的に自動化できない」と聞こえますが、そうではありません。 効かなかった理由はもっと単純です。

診断 書いていたのは全部形のテストでした。行数、主キーの一意性、NULL の有無。 qualify はこれを全部満たします。重複を消せば形は整うからです。 効かなかったのは、値のテストが 1 本も無かったから。

1. 形の照合を、値の照合に変える

出力の《値》を、モデルの計算経路を通らずにソースから独立に組み直して突き合わせます。 行数と主キーが正しくても、値が別の行から拾われていればここで落ちます。 

-- data-tests/assert_supply_cost_reconciles.sql
with expected as (
    select product_id, sum(supply_cost) as supply_cost
    from {{ ref('stg_supplies') }} group by product_id
),
actual as (
    -- 同じ SKU なら必ず同じ値のはずなので min と max の両方を見る
    select product_id, min(supply_cost) as min_cost, max(supply_cost) as max_cost
    from {{ ref('fct_order_items') }} group by product_id
)
select * from actual join expected using (product_id)
where abs(min_cost - expected.supply_cost) > 0.001
   or abs(max_cost - expected.supply_cost) > 0.001

同じ qualify を当て直すと、今度は落ちます。

Failure in test assert_supply_cost_reconciles
  Got 10 results, configured to fail if != 0

Done. PASS=38 ERROR=1 SKIP=11

SKIP=11 に注目。dbt build はテストが落ちた時点で下流を止めるので、 壊れた値が fct_orders や dim_customers に伝播しません。

2. 禁止パターンの判定を、LLM から機械に移す

4 周目を止めたのは dbt-reviewer、つまり LLM の判断でした。 そこが最後の砦なのは心細い。git diff の追加行を見るだけの決定論的なリンタに降ろせます。 

=== VERIFY RESULT ===
status: NEEDS_JUSTIFICATION

  fct_order_items.sql:43  [qualify]
    qualify row_number() over (partition by order_item_id order by supply_cost) = 1
    → row_number() で 1 行に絞ると、残った行以外の値が捨てられる。

正当な理由があるなら、その行に `loop-ok: <理由>` を書いて再実行する。

このリンタは「常に間違い」とは言いません。distinct が正しい場面はあります。 該当行に loop-ok: 理由 と書けば通る。 黙って通ることはできないという形にして、 ショートカットを記録された判断に変えるのが狙いです。

3. ゲートは一方向にしか動かない

そして本命がこれです。1 も 2 も、4 周目を体験したあとで初めて書けたものでした。 先回りしてすべてのテストを書くことはできません。だから運用のルールにします。

演習リポジトリでは、この 2 つを ./bin/ratchet.sh で後から入れる構成にしてあります。 先に入れてしまうと、4 周目で騙される体験ができないからです。

それでも残るもの

5 周目の any_value は、この方法でも自動では判定できません。 「顧客は 1 店舗にしか紐づかない」という不変条件が、 どこにも書かれていないからです。書かれていないものは照合できません。

ここだけは順序が逆で、気づいた瞬間に書くしかありません。 relationships でも unique でもいいので、 「たまたま正しい」を「保証されている」に変えておく。 ループにできるのは、この列には宣言されていない前提があると申し送ることまでです。

ループが解決してくれない 3 つのこと

Addy は元記事の最後に Loop gets better ≠ Problems get easier と書いています。 むしろ 3 つの問題は鋭くなる、と。今回の演習でも、そのまま起きました。

1. Verification ─ 「終わった」は主張であって証明ではない

4 周目がまさにこれでした。テストは全部緑、行数も主キーも正しい。それでも値は 15〜40 倍ズレていた。 ゲートは「失敗が報告されなくなった」ことしか判定できません。

2. Comprehension Debt ─ 理解の負債

ループが速くコードを出すほど、実装内容と自分の理解の差が開いていきます。 今回は 6 周・5 ファイルなのでまだ全部読めますが、50 周・30 ファイルだったら？

対策として LOOP_STATE.md には「症状ではなく原因を書く」ことを義務づけ、 終了時にはテストで担保されていないことの申し送りを書かせています。 

## 終了時の申し送り

ゲートは緑だが、以下はテストで担保されていない。人間が見るべき箇所。

2. `fct_orders.count_order_items` は、明細のない注文 27 件で NULL になる。
   現在テストがないため緑のまま通っている。これが仕様どおりかは未確認。
3. `supply_cost` は「SKU 1 個あたりの副資材コスト合計」。
   明細の数量という概念がまだモデルに無いので、注文単位の原価は数量を無視している。

3. Cognitive Surrender ─ 認知的降伏

いちばん危ないのは、ループが回っていることに安心して、意見を持つのをやめることです。 PASS=49 / ERROR=0 は気持ちいい数字ですが、 その 49 のうち何本が本当に意味のあるテストなのかは、誰も保証していません。

最後に残る事実 テストがない場所は、常に緑です。

まとめ

  • dbt のエラー対応は構造がいつも同じなので、ループにする価値がある。
  • 最初に決めるのはプロンプトではなく停止条件。verify.sh の終了コードがそれ。
  • エージェントが採点基準を書き換えられる状態にしない。契約はハッシュで固定する。
  • プロジェクト固有の前提（粒度・規約・やってはいけない直し方）は Skill に書き出す。
  • 作る役と検証する役を分け、検証役からは書き込み権限を取り上げる。
  • 構文エラーはループが片付ける。意味のエラーで人間の判断が要る。
  • ただし意味のエラーが自動化できないのではない。形のテストしか無かっただけ。値の照合に変えれば機械で止まる。
  • 監査で手を動かして数えたことは、その場でテストに昇格させる。ゲートは一方向にしか動かない。

レバレッジの効く場所が、プロンプトを書くことからループを設計することに移った ─ というのが元記事の主張です。 やってみて思うのは、ループ設計のほうが難しいということでした。 「何をもって完了とするか」を先に言語化しないと、そもそも書けないからです。
